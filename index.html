The pointer should travel,
not teleport.

Most computer-use agents screenshot the screen, guess a coordinate, then jump the cursor there. Human Input gives the model real Windows input primitives instead — eased cursor paths with an arc and a little jitter, genuine press and release, drag, per-character typing, and screenshots it can measure.

The problem

Screenshot-guess-click is slow, and it misses.

A vision model reading a 1920×1080 screenshot localises a target to maybe ±10 pixels. That is fine for a big button and fatal for a 16 px toolbar icon. Worse, a teleporting cursor simply is not accepted by a lot of software.

Teleports break apps

Drawing tools draw a straight line across the canvas. Drag-and-drop never receives the intermediate mousemove events. Games and remote desktops see physically impossible motion.

Every step costs inference

Screenshot, infer, act, screenshot, infer. A ten-step form becomes twenty model round trips. Input primitives can be batched into one human_script call.

No correction loop

Without seeing the result, the agent cannot tell whether the click landed. human_screenshot returns the actual image with a measurable grid.

The surface

Five tools, twenty-eight actions.

Small enough to fit in a model's context, complete enough to drive a real desktop session.

human_pointer — the mouse ▶
actionwhat it does
moveTravel to absolute screen coordinates along an eased, bowed path
move_byRelative move — call it repeatedly for "nudge it over step by step"
clickSingle, double, right or middle click
click_atMove and click in one call — one round trip fewer
press / releaseHold a button down, let it go; combine for any hold duration
dragPress at A, travel to B, release — eased the whole way
scrollWheel, with randomised intervals between notches
pos / screenRead the cursor position / the screen size
 
// travel, then click where you arrived
human_pointer { action: "move", x: 640, y: 360, durationMs: 600 }
human_pointer { action: "drag", from: { x: 200, y: 200 }, to: { x: 900, y: 600 } }
human_keyboard — the keyboard ▶ 
// per-character typing, CJK included, randomised gaps
human_keyboard { action: "type", text: "hello, 世界", delayMs: 40 }

// key combinations
human_keyboard { action: "key", combo: "ctrl+shift+esc" }

Accepts ctrl, shift, alt, win, enter, tab, esc, f1–f12, arrows, pageup/pagedown, letters, digits and punctuation.

human_window — window awareness, no screenshot ▶ 
human_window { action: "list" }                     // title, rect, hwnd, pid
human_window { action: "list", filter: "chrome" }  // title substring
human_window { action: "active" }                   // foreground window
human_window { action: "focus", hwnd: 393530 }       // bring to front

human_screenshot — letting the model see ▶

Returns the image itself, not a path. With zoom, a red grid line is drawn every 100 screen pixels — measure in the image, divide by the zoom factor, add the region origin, and you have an exact screen coordinate. 

human_screenshot { }                                                  // full screen
human_screenshot { x: 600, y: 300, width: 200, height: 150 }       // region
human_screenshot { x: 600, y: 300, width: 200, height: 150, zoom: 4 }  // magnified + grid
Under the hood

One resident process, real Win32 events.

The plugin is two files. index.js registers the tools and speaks one-line JSON to a long-lived PowerShell process; that process owns the actual user32.dll calls.

Why a resident driver

Starting PowerShell and running Add-Type costs about 700 ms. Paying that on every tool call would make "nudge the cursor" unusable, so the driver boots once and stays alive for the life of the plugin.

Why real Win32 injection

SetCursorPos, mouse_event and SendInput go through the system input path. Foreground applications receive genuine mouse and keyboard messages rather than synthetic events a framework has to special-case.

Why the path matters

The driver computes a quadratic Bezier bow, walks it with an easeInOutCubic curve, adds mid-path jitter that decays toward both ends, and settles with a tiny overshoot correction.

Why UTF-8 everywhere

PowerShell 5.1 decodes stdin as GBK by default, which turned any Chinese input into mojibake before it reached JSON.parse. Both streams are forced to UTF-8 without a BOM.

Straight talk

What it deliberately does not do.

!Windows only. The driver is built on user32.dll and gdi32.dll. There is no macOS or Linux path, and no plan for one.
!Elevated windows block it. When Task Manager or a UAC prompt is in the foreground, Windows drops injection from a non-elevated process — UIPI working as designed. Run the host elevated if you need to drive elevated windows.
!Needs an interactive desktop. Locked screens, logged-out sessions and Session 0 services cannot receive input.
!It sees pixels, not semantics. human_screenshot does not read the accessibility tree. Pair it with a DOM or UIA tool when you need structure rather than an image.
!One driver per desktop. Two plugin instances mean two drivers fighting over the single physical cursor.
Get started

Install, verify, drive.

# 1. install from GitHub
dsh plugin --profile <your-profile> add github:20700499ww-byte/dsh-plugin-human-input

# 2. confirm the bundle layer is present
dsh --profile <your-profile> --dump-config
# expect a "# == dsh-plugin-human-input" layer

# 3. from a model session, ask for a gesture
#    "move the cursor to the search box, click it, and type hello"

Requirements: Windows 10/11, Node.js ≥ 20, DeepSeek Harness >=0.2.0-rc.5 <0.3.0, and an unlocked interactive session. No native build step, no runtime network access.
